# Agent traffic

Agent traffic is automated web activity generated by software agents, crawlers, browser automation, and other machine clients. Agents can create traffic patterns that differ sharply from ordinary interactive browsing because one user request may fan out into many searches, comparisons, retries, and parallel operations.

## Expect machine-scale behavior

Common operational effects include:

- parallel retrieval across many candidates;
- high-frequency polling for changing state;
- retry bursts after timeouts;
- repeated comparison or quote requests;
- expensive dynamic rendering or search operations;
- long-running sessions that revisit resources;
- many small paid or metered operations.

A legitimate agent can therefore overload a service without malicious intent.

## Identify before applying policy

When possible, combine network and application signals with cryptographic [automated client identity](../trust/automated-client-identity.md). The IETF Web Bot Auth work explicitly includes operational use cases such as recognizing automated clients and applying differentiated policy.

Do not depend on a claimed user-agent name as the sole identity mechanism. Anonymous clients may still be allowed, but their quotas should reflect the uncertainty and abuse risk.

## Rate-limit work, not just requests

A request counter is insufficient when endpoints have very different costs. Track dimensions that represent the protected resource, such as:

- requests per client or delegated subject;
- concurrent operations;
- expensive searches or renders;
- tokens, compute time, or third-party API cost;
- mutation count;
- payment or checkout attempts.

Apply limits at the narrowest trustworthy identity available while retaining global safeguards against distributed abuse.

## Make retries safe

Agents frequently retry after uncertain failures. Consequential operations should use idempotency keys or an equivalent operation identity so a network timeout does not duplicate a purchase, booking, message, or state change.

[Agent reliability](../../operations/reliability/agent-reliability.md) covers retries and idempotency; [spending limits](../../infrastructure/economics/spending-limits.md) covers shared financial budgets.

## Return machine-actionable failure information

Use stable status codes and structured errors for throttling, unavailable dependencies, stale state, invalid authorization, and retryable failures. If a limit resets at a known time, expose that through the relevant protocol or API contract rather than requiring the agent to infer it from prose.

Observability should preserve the automated caller, delegated user where applicable, operation identity, resource cost, policy decision, and final outcome. This makes agent traffic diagnosable without treating every automated request as hostile.
