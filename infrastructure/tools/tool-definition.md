# Tools

A tool is an operation that an agent runtime can invoke through a defined interface. It connects generated decisions to capabilities such as searching records, reading files, calculating values, or updating a task. The model receives a description of the operation; an executor provides its implementation.

A useful definition states the operation's name, purpose, arguments, and expected result. For example, this application-level description separates one exact lookup from a broad search:

```json
{
  "name": "get_task",
  "description": "Read a task by its exact visible key.",
  "input_schema": {
    "type": "object",
    "properties": {"key": {"type": "string"}},
    "required": ["key"],
    "additionalProperties": false
  }
}
```

This is an illustrative application schema, not a universal wire format. Providers and protocols encode definitions differently: [OpenAI function calling](https://developers.openai.com/api/docs/guides/function-calling) uses `parameters`; [MCP tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools) uses `inputSchema`.

## Design a clear contract

Prefer operations with specific effects and explicit identities. A task lookup should return the task key, relevant fields, and a useful failure when it is unavailable. A status update should state whether it changes only status or also assigns work, triggers notifications, or schedules follow-up actions.

Separate model-supplied arguments from trusted execution context. The authenticated user and workspace usually come from the application, not from arguments the model chooses.

A tool is not inherently a remote service. It may be a local function, a sandboxed command, an HTTP operation, or an MCP call. Its transport and location do not determine whether it is read-only, authorized, or safe to retry.

## Compare interfaces for the same task

Suppose the request is “Assign T-42 to Mila.” These are **application-design alternatives**, not vendor APIs:

| Choice | Generic interface | Task-shaped interface |
| --- | --- | --- |
| Resolve the task | `list_records(table, filter)` with broad records | `get_task(key)` with identity, assignee, and revision |
| Resolve the person | Overlapping `search`, `lookup`, and `list_users` | `find_assignable_people(task_id, query)` with bounded candidates |
| Apply the change | `patch_record(table, id, arbitrary_fields)` | `assign_task(task_id, assignee_id, expected_revision)` |
| Result | “OK” or a full database object | Applied/not-applied outcome, target, new revision, operation receipt |

A domain-specific tool makes its purpose and permitted effect inspectable. It does not eliminate entity ambiguity: two assignable people named Mila require clarification, not arbitrary selection. The server still obtains the actor from trusted context, checks current permissions, and rejects stale revisions. A stable operation key is assigned by the application and reused for delivery retries; it is not regenerated by the model.

Return enough evidence for the next decision without dumping unrelated fields. Distinguish “no visible match,” “multiple candidates,” “stale revision,” and “temporarily unavailable” where doing so does not disclose forbidden resources. Explain retryability through the application contract, not an ambiguous natural-language error.

Do not turn every multi-step task into one opaque mega-tool. Keep separately approvable or irreversible effects distinct. A broad interface can still be appropriate in a restricted analyst sandbox; compare it on representative tasks rather than assuming that fewer tools or fewer calls always wins. [Anthropic's tool-design guidance](https://www.anthropic.com/engineering/writing-tools-for-agents) motivates evaluating tool usability as well as executor correctness.
